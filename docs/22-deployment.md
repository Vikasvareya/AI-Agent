# Deployment

The framework supports Docker Compose and Kubernetes deployment.

These are deployment examples, not evidence of production readiness or
high-availability support. See [Deployment and Operations](./DEPLOYMENT_AND_OPERATIONS.md)
and [Known Limitations](./KNOWN_LIMITATIONS.md) for the authoritative
constraints, including process-local state and required external services.

## Docker

Build and run:

```bash
docker build -t ai-agent-framework:latest .
export AI_AGENT_ADMIN_TOKEN="replace-with-a-long-random-admin-token"
export AI_AGENT_USER_TOKEN="replace-with-a-long-random-user-token"
export AI_AGENT_DB_PASSWORD="URL-safe-random-database-password"
docker compose up -d
```

Docker Compose builds the React/Vite chat UI and runs PostgreSQL for durable
chat conversations. The chat is at `http://localhost:8081/chat/`, the coding
workspace at `http://localhost:8081/coding/`, and the workflow control plane at
`http://localhost:8081/`. Use a URL-safe database password in
`AI_AGENT_DB_PASSWORD` because Compose places it in the PostgreSQL connection
URL. Compose's database volume is separate from the Ollama model volume.

Health endpoints:

- `GET /health/live`
- `GET /health/ready`
- `GET /metrics`

## Model selection and capabilities

The chat UI lists models installed on the configured Ollama server and lets
each user select one for a message. The API default is set by `OLLAMA_MODEL`;
`OLLAMA_HOST` points to the Ollama server. In Docker Compose these are configured
for the `ollama` service, with `llama3.2` as the default. Models are not pulled
automatically. For example:

```bash
docker compose exec ollama ollama pull llama3.2
```

Use `/v1/chat/models` to inspect installed models or
`/v1/chat/models?refresh=true` to bypass the short provider-side cache. Coding
mode changes the assistant prompt but does not execute code. Image and video
controls are intentionally unavailable until corresponding generation
providers are implemented and configured; no media is generated by the current
service.

## Project coding agent

The separate project coding agent is disabled unless
`AI_AGENT_CODING_WORKSPACE` points to a source workspace. It is restricted to
administrator credentials. For local development:

```powershell
$env:AI_AGENT_CODING_WORKSPACE = (Get-Location).Path
python -m app.api.server_main
```

The agent reads only selected, allowlisted text files and returns a validated
patch proposal. Manual review is the default; administrators explicitly apply
or reject each pending proposal. An administrator can opt into auto mode, which
applies validated patches only inside the configured workspace. Shell commands
and external plugin/MCP execution are not enabled. In container deployments,
mount only the intended project directory at a dedicated path and set
`AI_AGENT_CODING_WORKSPACE` to that path. Use a read-only mount for proposal-only
access; manual apply or auto mode requires a writable mount. Coding generation
has a separate 180-second default timeout, configurable with
`AI_AGENT_CODING_TIMEOUT`. The server stores permission mode, pending
proposals, and proposal audit events in the configured chat database. Pending
proposals are recoverable with `GET /v1/coding/proposals`; an apply interrupted
by restart is invalidated rather than replayed.
Do not expose the API's local-development administrator mode to untrusted
networks, and do not provide workspace files that administrators are not
authorized to send to the configured model provider.

Coding projects are limited to the configured workspace root and its direct
child folders. The editor supports allowlisted text files up to 32 KiB,
explicit saves with stale-file checks, and a sandboxed HTML preview. Coding
sessions and their bounded context are persisted in the configured chat
database; public read-only share links are opt-in, revocable, and expire after
seven days. Treat shared links as bearer credentials.

## Optional web search

Chat web search is disabled until `AI_AGENT_BRAVE_SEARCH_API_KEY` is provided
through a secret manager or the process environment. The user must enable web
search and enter separate search terms for each message. Only those terms are
sent to Brave Search; the full chat prompt is not. Common credential and
source-code patterns are rejected, but users should still avoid entering
private information. Search results are treated as untrusted model context and
the assistant response includes source URLs. Do not commit the API key to the
repository or expose it to the browser.

## Kubernetes

Apply all manifests:

```bash
kubectl apply -f deploy/kubernetes/
```

The deployment includes:

- Rolling updates with zero unavailable replicas
- Liveness and readiness probes
- CPU/memory/ephemeral-storage requests and limits
- ConfigMaps and Secrets
- CPU-based horizontal pod autoscaling

Before production, replace the example tokens in `secret.yaml` and use an
external secret manager or sealed secret mechanism.

Set separate `AI_AGENT_ADMIN_TOKEN` and `AI_AGENT_USER_TOKEN` values. The API
server listens on port 8081 while health probes use port 8080. Docker Compose
requires both tokens and `AI_AGENT_DB_PASSWORD` to be set in the environment.
For multiple accounts or tenants, configure `AI_AGENT_USER_TOKENS` as a JSON
map from each user credential to a stable tenant-qualified subject. Do not
share the legacy `AI_AGENT_USER_TOKEN` across users: holders of one token share
the same chat identity and history.

Kubernetes chat storage requires a managed PostgreSQL database. Replace the
example `AI_AGENT_CHAT_DATABASE` DSN in `secret.yaml` with a secret-manager
value before applying the deployment; the app's per-process connection pool is
bounded at 20. The checked-in PVC is not a database and must not be used to
share SQLite between replicas. Set `AI_AGENT_COOKIE_SECURE=true` when HTTPS is
terminated at the ingress.

The current Python HTTP server, workflow execution, and rate limiter are
process-local. PostgreSQL can persist conversations, REST workflow snapshots,
and coding-agent records, but horizontal execution is not coordinated.
Production traffic still requires shared rate limiting, load testing,
identity/tenant lifecycle management, and provider scaling/capacity controls.
Do not treat the sample Kubernetes manifests as a completed high-availability
or heavy-traffic deployment.
